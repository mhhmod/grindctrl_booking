01, the shared system

This note covers what all three pages share. Build these pieces first, because the landing, try-on and pricing pages are all put together from them.

Where the code goes. Keep the repo's structure and extend it. Don't start a parallel app. Pages stay in `app/page.tsx`, `app/try-on/page.tsx` and `app/pricing/page.tsx`. The landing and pricing pages keep wrapping themselves in `LandingLocaleProvider` with the exact root class string the golden guard test checks. Shared pieces for this design go in a new folder, `components/site/`, for the header, footer, language switch, password chip, background wiring and icon set. The landing story goes in `components/landing/story/`. The new public try-on page goes in `components/try-on/page/`. The pricing page is rebuilt in place in `components/pricing/`. The embedded storefront try-on at `app/embed/try-on` must keep working exactly as it does today. It shares `TryOnDemo`, `TryOnLocaleProvider` and `TryOnResult` with the current public page, so the new public page gets its own components and only shares logic modules such as the API client, the poll policy, the validator and the copy. Before adding any new primitive, check `components/ui` first, as `AGENTS.md` asks. Say in the pull request which existing pattern you checked and why it didn't fit. Never run the Launch UI shadcn command.

One header for the whole marketing site. The new header replaces `components/landing/site-header.tsx` everywhere it is used today. That includes the landing and pricing pages, and also `/roi`, `/security`, `/shopping`, `/conversations`, `/operations` and `/integrations` through `components/marketing/page-primitives.tsx` and the ROI page. On every page except the landing, the story items link to the landing with a hash: `/#try`, `/#store`, `/#ops`, `/#product`, `/#results` and `/#journey`. The old hashes that may still be out in the wild map to new ones: `#how` goes to `#journey`, `#demo` to `#try` and `#benefits` to `#product`. The landing handles those on load and on `hashchange`.

Tokens and colour. Every colour in the design already exists as a token in `app/globals.css`, apart from a few that are listed in `tokens.json`. Ink `#201d1b` is `--foreground` and `--primary`. The cream background `#f0ece8` is `--background`. Card `#f6f3ee` is `--card`. The soft grey `#e3dfda` is `--secondary`, `--muted` and `--accent`. Muted text `#66625f` is `--muted-foreground`. The line colour `#d4d0cb` is `--border`. Add the new ones to the landing token block, with the dark values suggested in `tokens.json`. They are `--gc-studio` `#ebe7e2` for the image wells behind garments and photos, `--gc-chip` `#e8e4df` for the small eyebrow chips, `--gc-text-2` `#4d4946` for captions, `--gc-inactive` `#9a958f` for arrows and later steps, `--gc-error` `#8a2f1f` for validation messages, `--gc-sheet-store` `#e9e5e0` for the store scene background and `--gc-sheet-dark` `#1c1a18` for the AI operations scene. The AI operations scene stays dark in both themes. Scope token overrides to it the way `.gc-auth-brand` does today, so its cards, borders and text use cream on ink in the light theme too. Don't hard code hex values in components. Use the tokens through Tailwind utilities, for example `bg-card`, `text-muted-foreground`, `border-border`, or through the new CSS variables.

Type. Manrope Variable is already the Latin face and IBM Plex Sans Arabic is already the Arabic face through `--font-arabic` and the `:lang(ar)` rule. That rule also removes letter spacing and uppercase, which the design needs. The landing hero heading is 66px on desktop and 40px on phones, weight 700, line height 1.06, tracking minus 0.04em. Landing scene headings are 48px on desktop with tracking minus 0.035em, and 28 to 32px on phones. The try-on heading is 44px and 30px, and the pricing heading is 50px and 32px. Pricing section headings are 40px and 28px. Use the golden scale `text-[28px] sm:text-4xl lg:text-[44px]` for section headings wherever the design is within 4px of it. The story captions use `clamp(28px, 2.5vw, 36px)`. Body copy is 15 to 17px at line height 1.5, and captions, chips and meters are 12 to 13.5px. Digits stay Western in both languages, matching the current pricing formatter and its `latn` numbering.

Icons and brand marks. The design uses its own small line icon set. Every icon is in `assets/icons` on a 24px grid, with a 1.8 stroke, round caps and joins, and `currentColor`. Port the set into one module, for example `components/site/icons.tsx`, with one component per icon, sized with a `size` prop and always `aria-hidden`. For the Shopify, n8n and HubSpot marks, use `components/brand-marks.tsx`, which already renders their official simple-icons shapes. The monochrome drawings in `assets/icons/brand` are only there for comparison. The GrindCTRL mark is in the same folder in ink and cream. Things named in the interface are shown with a mark as well as words. The AI agent is a sparkle in a filled circle. The team is two overlapping avatars with the initials O and N. A handoff is an arrow going into a person. Store knowledge is a book, order status is the Shopify mark, and the dashboard is bars. Arrows that point forward flip in Arabic. Mark them the way the repo already does, with `data-icon="inline-end"` and `rtl:-scale-x-100`, which the existing RTL test checks. External link arrows don't flip.

The header on desktop. It is a floating pill, fixed 18px from the top and centred. Its width is `min(1240px, 100% - 40px)`, its height 62px, and its padding is 20px at the start and 9px at the end. It is fully rounded, with a 1px border in the border token and the card colour at 86% opacity behind a 12px backdrop blur. Its shadow is `0 10px 30px -22px` in ink at 40%. At the start sit the GrindCTRL mark at 36 by 24 and the word GRINDCTRL, 15px, weight 800, tracking 0.1em. The middle holds the navigation, 14px weight 500, in `--gc-text-2`. The end holds the language switch, then the new Sign in link, then Book a call. Book a call is ink with cream text, 44px tall with 20px side padding and fully rounded, and it opens `BOOKING_URL` in a new tab. Sign in is a text link styled like the language switch, 40px tall, pointing to `/sign-in`. Its copy already exists as `signIn` in `lib/landing/landing-i18n.ts`, in English and Arabic. A translucent hover pill, ink at 7% and 38px tall, glides under the hovered item in 0.38s with the house ease. A 4px ink dot under the current item marks where you are in the story. Below 1180px wide, the last two items, How it works and Pricing, leave the bar, as in the design. The pricing page uses the same header, but its middle holds three in-page tabs instead: Plans, Top-ups and Questions, each with its icon. The try-on page has its own header, described in `03-try-on.md`. The sign-in guard applies to the landing header, so the try-on header doesn't need Sign in.

The header on phones. It is a pill fixed 12px from the top and sides, 58px tall, with the card colour at 90% opacity and a slightly deeper shadow. It holds the mark and the word GRINDCTRL at 13.5px, then Book a call as a 44px ink pill, then a 44px round menu button. The menu button's two bars turn into a cross in 0.3s. Below 360px wide, hide the word GRINDCTRL and keep the mark, so everything fits at 320 without clipping. On the landing, a thin progress bar with five segments sits centred under the header, 76px from the top, and shows how far through the story you are. The menu opens as a rounded sheet under the header over a dim backdrop. Its first row is Sign in, with the person icon, going to `/sign-in`. Then come the rows for each scene with their icons, Ask the store and Pricing. The language switch and Book a call sit at the bottom. Every row is 50px tall with a 34px icon tile. On the pricing page the phone header is the same, and its menu lists Sign in, then Plans, Top-ups and Questions, then Home and the try-on page, then the language switch. The menu must behave like a real dialog. Opening it moves focus to its first row and keeps Tab inside it. Escape and the backdrop close it, focus returns to the menu button, and the page behind can't scroll while it's open. Keep closed menu content out of the DOM, so tests and screen readers never find hidden rows. The design leaves all of this out, so add it.

The footer. It holds the mark, a row of links, and the language pair, with the current language marked with `aria-current`. Each page has its own set of links. The landing links to Product and Live store inside the story, then to the try-on page, Pricing, ROI calculator and Security. The pricing page links to Home, Live demo (the try-on page), Pricing, ROI calculator and Security. The try-on page links to Home and Pricing. These are all routes of this same app, so they open in the same tab, even though the prototype sent ROI and Security to grindctrl.cloud in a new tab. The footer must keep the existing analytics consent control, the theme toggle and the spacing reserved for the assistant launcher, because PostHog stays opted out until a visitor agrees there. `SiteFooter` and `AnalyticsConsentControl` read the locale through `useLandingLocale`, which doesn't exist under the try-on page's `TryOnLocaleProvider`. So make the new footer take the locale and its links as props, and give the consent control a way to receive the locale as well. The try-on page has no footer in the design. Give it the compact footer so it has a way home, the theme toggle and the consent control.

The language switch and right to left. The server already resolves the language from the `gc-locale` cookie, then from `Accept-Language`, and renders `lang` and `dir` on `<html>`. Keep that, so the first paint is already in the right language. When someone switches, call `persistSiteLocale` from `lib/landing/site-locale-store.ts` and update the provider. Also set `document.documentElement.lang` and `dir` straight away, because menus and dialogs render in portals and otherwise keep the old direction until a reload. The switch must never reset the page. On the landing it keeps the current beat of the story. On the try-on page it keeps the chosen piece, the photo and any looks. On pricing it keeps the scroll position. The switch's label and accessible name are always written in the language it switches to, as `copy/*.json` lists under `languageSwitch`. A few things stay in English in both languages: GRINDCTRL, product names from the store, pack names such as Boost 80, the store domain, the password, email addresses and the short EN label in the hero chat. All the Arabic is in `copy/*.json`, including the `additions` blocks. The only exceptions are the few existing repo strings each note names, such as `signIn`, the try-on privacy line and the try-on error copy. Put new strings into the repo's existing typed copy objects, following their flat camelCase naming with a section prefix: `lib/landing/landing-i18n.ts`, `lib/try-on/i18n.ts` and `components/pricing/pricing-copy.ts`. Don't machine translate anything and don't invent copy. If a string you need is missing, stop and list it in the pull request.

Mirroring rules. Build layouts with logical properties so the reading order flips on its own, for example `ps-`, `pe-`, `ms-`, `me-`, `start-`, `end-` and `text-start`. Some pieces are placed by coordinates rather than by flow, and each of these is mirrored in Arabic as a whole. That covers the AI operations graph, the product stack map, the credit fork on pricing, the background wiring and the story rail. The prototype mirrors these with an `rtl` flag that reflects each x position, as `width - x`, and flips the connecting SVG paths. Flip decorative SVGs with a horizontal scale of minus one. Bars and meters fill from the right in Arabic. The scene rail and scroll cue move to the left edge in Arabic, and the background trace log moves to the right edge. The live store window stays left to right and in English in both languages, because it shows the store as the store really is.

Responsive rules. The prototype switched between phone and desktop at 1000px for the landing and 900px for the other two pages, and it shrank the desktop layout with CSS zoom in between. Production uses one switch point, Tailwind `lg` at 1024px, and never uses CSS zoom. Below `lg` the phone layouts are used, centred in a column no wider than 560px, so tablets in portrait look intentional rather than stretched. From `lg`, the desktop layouts sit inside the standard container `mx-auto w-full max-w-7xl px-4 sm:px-6 lg:px-8` and use fluid grids. Two grids need an extra step between `lg` and `xl` (1280px) because the container is only about 960px wide there. The pricing plans sit two by two from `lg` to `xl` and in four columns from `xl`. The try-on studio's piece and photo columns are 260px with 48px joiners from `lg` to `xl`, and 300px with 56px joiners from `xl`. The landing story blocks are drawings of product screens with a fixed inner layout. Scale them as whole blocks with a transform, using the fit rules in `02-landing.md`, rather than reflowing their insides. On tablets the fit and the card spread use the 560px column width, not the viewport. Viewports shorter than 560px, such as phones in landscape, show the story as stacked sections, the same way reduced motion does. Check every page at 320, 343, 360, 375, 390, 414, 768, 1024, 1280, 1440 and 1920 wide, and at 844 by 390 in landscape. There must never be a sideways scroll, and no text may be clipped. Every tap target is at least 44px, and primary buttons on phones are 48px. Fixed headers respect `env(safe-area-inset-top)`. Full screen story sheets use `100svh` for layout, and `100dvh` only where the design needs the moving toolbar space.

Motion. The house ease is `cubic-bezier(0.22, 1, 0.36, 1)`. Image wipes use `cubic-bezier(0.65, 0, 0.35, 1)`. Small state changes take 0.3s, cards and captions 0.45 to 0.6s, and image reveals and pointer glides 0.8 to 0.95s. The golden standard approves only four motion classes today. This design adds the landing story system and a set of keyframes the prototype defines and uses. They are reveal, swap and rise for images and text, drop for the photo landing in the store panel, drift and floor for the hero stage, cue for the scroll hint, invite for the untouched garment, typing for the chat, pop for counters, a ring on the store's Generate button, tap for the replay pointer, pulses along the background wiring, a live dot, flowing connector dashes, a progress sweep on the active list item, grow for new path segments on phones, and fade and menu entrances. Add them to `docs/golden-landing-standard.md` at the repo root as the approved story motion set. Give the reason: a paced product story can't be built from reveal-on-scroll classes alone. The blocks after the story that rise into place must use `lib/landing/use-scroll-reveal.ts`, as that document requires. `app/globals.css` gives many elements a 220ms colour and box-shadow transition. Opt the elements the director writes every frame out of it, or the story will lag behind the scroll. Under `prefers-reduced-motion: reduce` there is no movement, no loop and no scroll pacing, and every state shows its end frame. Short opacity and colour transitions may stay, because `app/globals.motion.test.ts` requires that reduced motion keeps that kind of feedback.

The background wiring. Behind each scene sits a quiet layer of thin lines, small square nodes and pulses running along the lines. It suggests the system working underneath without using any words. It is purely decorative, so mark it `aria-hidden` and keep it out of the tab order. On desktop it draws five lines and twelve nodes on a 1440 by 900 grid, and on phones two lines and six nodes on a 390 by 844 grid. The exact paths are in `design/prototype/generators/env11.py`. Lines are ink at 8.5% on light scenes and cream at 7.5% on the dark scene. Pulses are ink at 42% or cream at 50%, and nodes are ink at 14% or cream at 16%. Pulses run along each line every 9.5 to 14s. On desktops 1200px and wider, a short trace log in 10px text sits at the left edge and lights one line at a time every 3s, for example photo received, garment mapped, look rendered and added to cart. Each scene and page has its own four lines, and they are in the copy files. The layer is fixed to the viewport and clipped to its own scene, so lines continue across scenes as the sheets slide. Animate it only while its scene is on screen and the tab is visible. In Arabic the drawing is mirrored and the log moves to the right. If axe reports the faint trace text for contrast even though it is `aria-hidden`, draw it as SVG text inside the hidden layer rather than making it darker.

The store password chip. It sits next to every button that opens the live demo store: in the landing store scene, in the landing closing band and in the try-on page store strip. From the start it holds a key icon, the words Store password and the value 1 in a small box with a dashed ink border, then a copy button. The value is 18px, weight 800, `lang="en"`, and selects all of itself on one tap. The copy button is ink with cream text and reads Copy with a copy icon. After a successful copy it reads Copied with a tick for 2.2s. It uses `navigator.clipboard.writeText('1')`. If that is refused, it selects the value and tries `document.execCommand('copy')`. If that fails too, the value stays selected and the button reads Selected, press Ctrl+C. Announce the result politely to screen readers. These labels and their Arabic are already in the copy files. The chip is 50px tall on desktop and 48px on phones.

Accessibility. The design gets most labels right, but the prototype skipped a few things production needs. Each page gets a skip link to `main`, a single `main` landmark and one `h1`. Dialogs and the phone menu trap focus, close on Escape and return focus to where they opened. Story scenes that have slid off screen get the `inert` attribute, so keyboard focus never lands behind the current sheet. The product walkthrough panes that are hidden get `inert` too. The replay pointer in the landing's try-on and store scenes finds its targets through `data-` attributes, never through translated `aria-label` text. That was a bug in the Arabic prototype, where the pointer never appeared. Scripted demos say they are demos in words, and their live regions are polite. Colour contrast meets WCAG 2.2 AA, which the axe test enforces on every golden page in both languages.

Analytics. Keep using `trackClick` from `lib/analytics.ts` for every call to action. It takes a legacy event name and a properties object and reads the placement from `properties.section`. So a hero booking button calls `trackClick('cta_clicked', { cta: 'book_call', section: 'hero' })`. Plan buttons call `trackClick('plan_cta_clicked', { plan: planKey, section: 'pricing_plan' })`, and pack buttons call `trackClick('pack_cta_clicked', { pack: packKey, section: 'pricing_pack' })`. Free is tracked as a plan button, as it is today. Use these sections. On the landing: `header`, `hero`, `store_scene`, `final_cta` and `footer`. On pricing: `pricing_hero`, `pricing_plan`, `pricing_pack` and `pricing_closing`. On the try-on page: `try_on_header`, `try_on_result` and `try_on_store`. The `tryon.*` events in the taxonomy are scoped to a tenant and are dropped without a tenant and session, so don't send them from the public page. Instead, add a small exported helper next to `trackClick` that sends marketing events through the same consent-gated tracker. Use it for `storefront.demo_started` and `storefront.demo_completed` with `demo: 'try_on'` on the try-on page, and for `storefront.product_tab_engaged` when a product walkthrough tab is clicked. Never send the photo, the result image or any personal data.

The assistant launcher. `AssistantLauncher` is mounted in `app/layout.tsx`, outside the landing tree, and its visibility rules live in `lib/assistant/launcher-visibility.ts`. While the landing story is pinned, the story sets `data-story="pinned"` on `<html>`, and the launcher hides itself when that attribute is present. When the visitor reaches the rest of the page, the attribute is removed and the launcher comes back. Keep its focus restoration and its auth-route suppression exactly as they are.

Dark mode. Light is the designed reference and the only theme in the golden screenshots. Because everything is built on tokens, dark mode comes out legible without separate design work. The AI operations scene stays dark in both themes, and photos keep their own light backgrounds. Check both themes at 390 and 1440 in both languages, as the header guard in `AGENTS.md` asks.

Images and speed. Move the images you use from `assets/images` to `public/landing/v15/`, keeping their names, and render them with `next/image` with correct `sizes`. Mark the hero stage images as priority and lazy load everything below the first screen. The landing story has a lot of markup, so render each scene's heavy parts only when it is near the viewport. Drive per-frame motion by writing transforms to refs rather than through React state. Aim for a largest contentful paint under 2.5s on a mid-range phone over 4G, a cumulative layout shift under 0.1, and no long tasks over 200ms while scrolling the story.

Truthfulness and copy rules. Nothing on these pages may claim more than the product does, and every claim goes through `lib/product-truth` as it does today. The AI operations counters and the product walkthroughs are labelled Demo data. The hero chat is labelled Demo conversation. Sample try-on looks are labelled as sample looks made by the engine on AI-generated models. The store scene is a replay of the real demo store. Keep all of those labels in both languages. Two claims need the owner's sign-off before they ship, and the pull request must ask for it. The first is managed setup: the hero line We set it up and keep it running. and the Pro plan's done-for-you setup row. The register lists that claim as `service.managed-setup`, with approval required, on the landing hero and on pricing. Until the owner approves it in `lib/product-truth/public-register.ts`, render the hero without that sentence and show Pro with only its catalog description. The second is the pricing answer that says the try-on widget stops showing when credits run out. `05-backend.md` explains why that isn't true in code today. Copy never uses em dashes, gradient text or side-stripe borders. The one em dash in the prototype's copy has already been changed to a comma in `copy/landing.json`. If any error text you show from `lib/try-on/shopper-errors.ts` contains an em dash, change it to a comma or a full stop.
