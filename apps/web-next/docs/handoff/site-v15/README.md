GrindCTRL site v15, handoff for Claude Code

This folder holds everything needed to rebuild three public pages of `apps/web-next` from the approved v15 design. The pages are the landing page at `/`, the public try-on page at `/try-on` and the pricing page at `/pricing`. Each has to work in English and Arabic, left to right and right to left, on phones and on desktops, and each has to be wired to the real backend that already exists in this repo. Read this file first, then the six numbered notes in order. The notes are written as plain paragraphs on purpose, so read them top to bottom instead of skimming for headings.

The design lives on a Claude Design canvas the owner can open, called GrindCTRL Landing Page, Dark, at version 15. You can't open it, so this folder carries what you need from it. `design/screens` has reference screenshots of every state, grouped by page and then by layout and language: `desk-en`, `desk-ar`, `phone-en` and `phone-ar`. Desktop shots are 1440 by 900 and phone shots are 390 by 844 at twice the pixel density. The landing shots are numbered in story order, one per beat, then the sections after the story, then the open phone menu. The try-on shots walk through idle, ready, creating, done, the photo view, the piece picker, a second look, the compare view and a file that's too large. The pricing shots show the first screen, the full page and the questions with the second answer open.

`design/prototype` has the prototype itself. The `boards` folder holds the six built canvas files with their full markup and their logic class. The `logic` folder holds the runtime code on its own: `director11.js` paces the landing story, `render11.js` computes its values, and `tryon11.js` and `pricing11.js` run the other two pages. The `generators` folder holds the Python that produced the markup. The prototype refers to images as `/_blob/<hash>` paths, and `blob-to-file.json` maps each one to a file in `assets/images`. Treat all of this as a precise reference for sizes, spacing, timings and behaviour. None of it ships. The canvas runtime tags such as `sc-if`, `sc-for`, `x-dc`, `helmet` and the `{{ }}` holes mean nothing in this app.

`assets/images` has all 51 images the three pages use. `assets/manifest.json` gives each one's role, the pages it appears on and a suggested path under `public/landing/v15/`. `assets/icons` has the line icon set as standalone SVGs. `assets/icons/brand` has the monochrome Shopify, n8n and HubSpot marks and the GrindCTRL mark in ink and cream. `copy/landing.json`, `copy/tryon.json` and `copy/pricing.json` hold every visible and assistive string in English with its approved Arabic, in reading order and grouped by section. They also include the strings the page logic sets, and for the landing the scripted hero chat. `tokens.json` maps every design value to the tokens that already exist in `app/globals.css` and names the few that are new.

The six notes are these. `01-system.md` covers the shared foundations: tokens, type, icons and brand marks, header, footer, the language switch and right to left, responsive rules, motion, the background wiring, the password chip, accessibility, analytics and dark mode. `02-landing.md` covers the paced scroll story and everything after it. `03-try-on.md` covers the try-on page and its wiring to the real try-on API. `04-pricing.md` covers the pricing page and its wiring to the live plan catalog and currency logic. `05-backend.md` covers the one backend bug that stops the live store's try-on today and the exact fix, plus the API contracts the new pages use. `06-qa.md` lists what counts as done, which tests change and why, and the manual checks. `CLAUDE_CODE_PROMPT.md` is the prompt the owner will paste to start the work.

The owner has already made the following decisions, so treat them as settled. The scope is the three pages above. The older dark edition boards, Main and Mobile, are not part of this work. Sign in stays visible and translated in the desktop header beside the language switch. On phones Sign in becomes the first item in the menu, and the header keeps its single row with Book a call and the menu button. That change must also update the Landing sign in regression guard in `AGENTS.md` in the same pull request, and say why. The existing `gc-locale` cookie stays the only source of truth for language, and the prototype's `gc-lang` localStorage key is dropped. The existing USD and EGP pricing logic stays, including the cookie, geo lookup and toggle, and the new design gives the toggle a place. The try-on page sends uploaded photos through the real try-on endpoints. The sample model photos show stored outputs the engine made earlier, labelled as samples, with no pretend processing. The landing hero chat stays a scripted demo that is visibly labelled as a demo conversation and never calls an AI. The site assistant launcher keeps working as it does today. The only change is that it stays hidden while the landing story is pinned. The live store scene stays a replay built from real screenshots of the demo store. Its Open the live store button and copyable password lead to the real store at `https://grindctrl.myshopify.com`, whose password is 1. Light is the designed theme, but everything is built on tokens so dark mode stays legible, and the theme toggle stays in the footer. The new header replaces the old one on every marketing page that uses it, not only on these three.

Two questions are still open for the owner, and the pull request must ask them plainly. The first is whether the managed setup claim may ship. That covers the hero line We set it up and keep it running. and the Pro plan's done-for-you row. `lib/product-truth` marks it as needing the owner's approval, so until they approve it, both stay out. The second is the live pricing answer that says the try-on widget stops showing when credits run out. The storefront widget doesn't do that yet, so the owner should either get the widget fixed or change the answer.

Where the design and a repo rule disagree, the notes say which one wins. In short, repo rules about truthfulness, accessibility, tokens, logical properties, the landing root wrapper and the container width win. The design wins on layout, content order, visuals and interaction. Where the repo has an older visual rule that the new design replaces on purpose, such as the approved motion classes or the old hero heading in tests, update the rule or the test in the same change and say why. Never loosen a check to make it pass.

Work in this order. Pushing to `main` deploys to production, so everything goes through pull requests. First fix the try-on model bug from `05-backend.md` on its own branch from `main`, for example `fix/try-on-model-tier`, with its own pull request, so it can ship right away. Then make the redesign branch from `main`, for example `feat/site-v15`. Next build the shared pieces from `01-system.md`. Then the pricing page, because it is the smallest and fully data driven. Then the try-on page. The landing story comes last because it is the largest. Finish with the test updates, the new visual baselines and the manual checks in `06-qa.md`. Commit messages follow the repo's Conventional Commits style with a scope, such as `feat(landing): ...`, `feat(pricing): ...`, `feat(try-on): ...` and `fix(try-on): ...`.

The work is done when all three pages match the screenshots at 390 and 1440 in both languages. They must also hold together at every width from 320 to 1920 with no sideways scroll, and every link and button must do something real. The try-on page has to produce a real look from an uploaded photo when `TRYON_MODE=live`. The pricing page renders the live catalog in USD and EGP. Once the model fix is deployed, the store's own try-on generates again. The owner checks that last one, because the demo store only talks to production. Every check in `06-qa.md` has to pass, CI has to be green and the pull request has to carry before and after screenshots.
