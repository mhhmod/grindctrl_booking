First, where the shopper widgets live today. Both shopper widgets ship in one Shopify theme app extension, `apps/grindctrl-tryon/extensions/tryon-block` (type theme, `shopify.extension.toml`). It has one app block and two app embeds. The app block `blocks/tryon.liquid` targets product sections. It prints a button with the product handle, title, featured image and first variant as data attributes, and loads `assets/tryon.js` and `assets/tryon.css`. The embed `blocks/tryon-catalog.liquid` targets the body. It loads `assets/tryon-catalog.js`, which finds product cards and injects a "Try on" pill on each. The embed `blocks/messenger.liquid` targets the body too. It loads the Store Chat loader from `https://grindctrl.cloud/widget/v1/messenger.js` (source `apps/web-next/public/widget/v1/messenger.js`) with the shop domain, the locale and, for signed-in customers, their id, email and name. The rest of `apps/grindctrl-tryon` is configuration: `shopify.app.toml` (scopes, the App Proxy at `/apps/grindctrl` pointing to `https://grindctrl.cloud/api/shopify/proxy`, webhooks, redirect URLs) and a README. Its `PRODUCT.md` and `DESIGN.md` describe an old email campaign, not the extension. The admin app itself lives in `apps/web-next` at `/shopify/app`. `apps/clerk-mcp` is a small HTTP MCP server for Clerk's Backend API, an operator tool, and plays no part in v16.

The try-on interface is a cross-origin iframe of `https://grindctrl.cloud/embed/try-on`, served by `apps/web-next/app/embed/try-on/page.tsx` and built from `apps/web-next/components/try-on/try-on-demo.tsx`, `try-on-result.tsx` and `photo-upload.tsx`. On a product page, `tryon.js` first asks the App Proxy `/apps/grindctrl/try-on-context` (`apps/web-next/app/api/shopify/proxy/try-on-context/route.ts`) for a signed context. It then appends the iframe inline under the button and passes the context in the URL fragment. On a collection page, `tryon-catalog.js` opens the same iframe in a dialog. Both scripts style themselves from `/apps/grindctrl/config` (`apps/web-next/app/api/shopify/proxy/config/route.ts`), which reads `tryon_settings` through `apps/web-next/lib/try-on/settings.ts`. The embed turns the same settings into CSS variables with `apps/web-next/lib/try-on/appearance.ts`. Store Chat works differently. The loader draws a launcher in its own shadow root and creates an iframe of `https://grindctrl.cloud/embed/messenger` (`apps/web-next/app/embed/messenger/page.tsx`, which renders `apps/web-next/components/messenger/MessengerPanel.tsx`). It fetches config cross-origin from `/api/messenger/config`, not through the App Proxy, and uses the App Proxy only for `/apps/grindctrl/messenger-identity`. The files `apps/web-next/public/widget/v1/loader.js` and `runtime.js` belong to the older agent widget and are not part of v16. The website studio at `/try-on` (`apps/web-next/app/try-on/page.tsx` and `apps/web-next/components/try-on/page/*`) is GrindCTRL's own marketing surface, not a merchant widget.

v16 changes this shape in five ways. First, the try-on opens as a sheet on phones and as a centred dialog on desktop (TryOn-Result, TryOn-Desktop). `tryon.js` should open the iframe like the catalog dialog, as a full-height sheet with safe-area padding, instead of growing the product page inline (`tryon.js:231`). Second, the boards now name today's theme pieces and keep them: the GrindCTRL Try-On block (`blocks/tryon.liquid:51`), the "Try-On on product cards" embed (`blocks/tryon-catalog.liquid:16`) and the "GRINDCTRL Store Chat" embed (`blocks/messenger.liquid:32`), as Today-Setup, Shopify-Home-Setup and ChatStudio show. They no longer show a merged embed. The new features still need one small shared first-party loader on every page. It would own the visitor id, the preview token and holdout bucket (phase zero item 9), the event beacon (item 22), the theme token probe described below, the card pills, the floating "Making your look" chip and My looks (item 16), and the chat launcher. Load it from whichever embed is on, once per page, so stores keep the embeds they already enabled. Third, Store Chat gets a product-page block ("Questions about this abaya?"), so the extension needs a second app block, or the Try it on block also renders that row. Fourth, the widgets must talk to each other through the loader. The chat card's Try it on, the result's Ask about the fit, and Add to cart from chat all cross from one grindctrl.cloud iframe to the merchant page and back. Only the loader can call the merchant's own `/cart/add.js`, `/cart.js`, `/recommendations/products.json` and the App Proxy. Fifth, a shopper's photo and looks must render only inside our iframes, never in the merchant page's own DOM. Session-replay and analytics scripts on a store record the page DOM, and a look drawn there would let the store "see" a look the shopper never sent. That rules out swapping a product card's image for the look in the page itself (TryOn-Browse). The "Your look" card state should be a tiny iframe, or show no picture.

How merchant theme tokens could reach the widgets. Today nothing reads the theme. Try-on colours, radius and labels come from `tryon_settings`, chosen by the merchant from presets that include GrindCTRL-style colours (`apps/web-next/components/try-on/settings-controls.tsx:57-59`). The embed uses the app's own fonts and token sheet. The chat launcher defaults to GrindCTRL charcoal (`apps/web-next/lib/messenger/config.ts:40`). The boards want the button, text, background, font and corner radius to follow the store, for example "Matches your Add to cart button: Figtree, 12 px corners" and "Taken from your theme". There are three sources, and the build should use all three in order. The first is a runtime probe in the shared loader. On a product page it reads the computed style of the theme's Add to cart button (the submit control inside `form[action*="/cart/add"]`) and of the body: font family and weight, border radius, background and text colours, border. It passes them to each iframe in the URL fragment or by `postMessage`, where they become CSS variables. It also reports them to our server about once a day, so the dashboard previews and the contrast check ("18 to 1, Passes") use real values. The second is a server-side snapshot of the published theme's `config/settings_data.json`. That needs the `read_themes` scope (phase zero item 24), but it gives the dashboard values before the store has any traffic. The third is a merchant override in the Look sections of ChatStudio and TryOnStudio. Fonts need care. The iframe cannot use the theme's font unless it loads the font file itself. The probe can pass the font-face URL it finds in the page's stylesheets, but whether Shopify's font host allows cross-origin loading must be checked. The fallback is a system stack, never GrindCTRL's Manrope or Inter. The contrast ratio should be computed on the server with the WCAG formula, falling back to the theme's own text colour when a pair fails. Two small details matter here. The try-on iframe needs `allow="camera"` for the "Take a photo" path on TryOn-Photo; today the iframe is created without it (`tryon.js:174-177`). And the theme's Liquid may expose theme settings to app blocks, but setting names differ per theme, so the probe is the dependable path.
