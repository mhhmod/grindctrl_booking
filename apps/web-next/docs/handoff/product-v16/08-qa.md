This note says what counts as done for v16, which checks to add or change, and what has to be checked by hand. Each surface note ends with its own definition of done, and `06-phase-zero.md` gives each backend item its own tests. This note ties them together.

The overall bar. Every board in `design/screens` is built, and it matches its English screenshot and its Arabic twin's screenshot in `design/screens/<surface>/ar/` at 390 and 1440 pixels. It holds together at every width from 320 to 1920 with no sideways scroll and passes the responsive audit below in both directions. Every feature the boards outline as new ships only with its contract from `09-backend-contracts.md` and behind its flag. Every visible number comes from a named source or is absent. Every button and link does something real or is absent. Every data block has its loading, empty and failed state. Shopper surfaces carry the merchant's theme and never GrindCTRL's colours or branding. Nothing a screen promises is untrue, and that is what band one of phase zero guarantees, so no shopper-facing part of v16 ships before band one. CI is green, and nothing in CI was loosened to get there. Where a check is wrong rather than inconvenient, fix the check in the same change and say why, as `AGENTS.md` requires.

The automated checks that exist and must stay green are the ones `next-release-check.yml` runs. They are `npm test`, `npm run typecheck`, `npm run lint`, the Docker build, the golden Playwright specs and `mobile-overflow.spec.ts`. The golden specs cover the marketing pages, which v16 does not touch apart from Studio-Phone on `/try-on`. `golden-standard-try-on.spec.ts` pins parts of that page, so update it in the same change if the studio's copy or states change, and say why.

Add these automated checks. First, copy scans that run in CI. One fails on an em dash in any English or Arabic dictionary, Liquid file or widget script. One fails on Eastern Arabic digits in any Arabic string. One fails on "credits", "renders" or "generations" in merchant or shopper copy, since the unit is looks. One fails on any dictionary key that lacks either English or Arabic. One compares the shipped strings with the `copy` folder, so an approved Arabic string never drifts from `copy/arabic-approved.json`, and it prints the strings still marked draft so the pull request can list them. Second, a token test. Extend `components/mantine/theme.test.ts` for every new token, and add a contrast test that computes the WCAG ratio for each foreground and background pair in `tokens.json` in both themes. Third, unit tests for every phase zero item, as each item describes. The most important are the entitlement and launch-state answers of the config routes, the photo-promise provider flag and storage expiry, the handoff copy keyed on the alert outcome, the hours function across midnight, escalation routing over the labelled message table, retrieval of approved answers, phone normalisation for order lookup, shift resolution and the 10 minute backup, the funnel and attribution rollups with fixtures that reproduce the boards' arithmetic, and billing reconciliation.

Fourth, component tests for the dashboard, using `renderWithMantine`. Render each page's blocks with fixture data in all four states, for an owner and for a team member. Assert that a team member never receives Plan or any billing control, and that the server actions refuse them too. Fifth, Playwright specs for the shopper widgets, built on the pattern `messenger-embed.spec.ts` already uses: a host page with hostile CSS and every API call intercepted. Make that host page look like a real theme product page, with a sticky Add to cart bar on phones, a collection grid and a cart drawer. From it, reach every try-on state with the job API mocked: check failed, consent, making, busy with the queue, ready, colour switch, added, not right, failed, out of looks, My looks and Delete all. Reach every chat state: home, an answer with parts, Add, the signed-in and guest order flows, the four handoff states and offline with two queued messages. Assert the behaviour, not only the pixels. The bubble's box must never intersect the sticky bar. The pill and button must not appear when config says hidden. Focus must move into a sheet and back out. Escape must close it. The closed chat iframe must be out of the tab order. A layout shift observer must report no shift on the product page while the widgets load. And the host page's DOM must contain no URL of a look or a photo, which is the automated half of the privacy rule in `01-system.md`. Sixth, run axe on every widget state and every dashboard page in both languages, the way `golden-standard-a11y.spec.ts` does for the marketing pages. Seventh, an automated responsive audit, built on `mobile-overflow.spec.ts` or as a sibling spec, over every widget state, every dashboard page and every admin page. Run it at 320, 360, 375, 390, 414 and 430 pixels wide and at 375 by 667 for phones, at widths from 320 to 1920 for pages, and from 1024 by 768 up to 1920 by 1080 for storefront desktops, once left to right and once with `dir="rtl"` forced. At each size assert that the page has no horizontal scroll, that every sideways scroller stays inside its own track, that a fixed phone view scrolls only its middle while its header and composer stay pinned, that dialogs and sheets fit the viewport and scroll inside, that tap targets are at least 44 by 44 in the shopper widgets, 40 by 40 on the dashboard and 32 tall for Shopify controls, that no text renders under 12 pixels, that inputs are at least as tall as their content, and that numbers, codes, URLs and phone numbers keep their left to right order inside Arabic. Add a scan that fails on physical properties such as `margin-left`, `padding-right` or `text-align: left` in new CSS, and check that directional icons flip under `dir="rtl"`. Allow only the intended cases, each named in the spec by selector with its reason: a modal over the page (the Command palette, the try-on dialog on desktop, the photo sheet at 375 by 667), single line ellipses that carry a `title` (Inbox list previews, the chat sticky bar's product name at 320, the share URL), message boxes inside a scrolling chat list at 375 by 667, and an inline text link inside a sentence. Eighth, visual baselines for the widget states and the dashboard pages at 390 and 1440 in English and Arabic, with the twins' screenshots as the Arabic reference, updated through the existing `update-visual-baselines.yml` workflow and reviewed by eye, never accepted blindly. Ninth, a size budget for the storefront scripts. Record today's compressed size of the loader and the try-on assets, and fail CI if a change grows them past a budget the pull request states.

The dashboard needs a signed-in user for end-to-end tests, and the repo has no such spec yet. If the owner provides a Clerk development instance, use Clerk's testing helpers for Playwright to sign in a test user. Never add a bypass to production code. Without that, keep the dashboard covered by component tests and say so in the pull request.

Manual checks, because some things only a real device shows. Try the storefront widgets on a real iPhone in Safari and a real Android phone in Chrome, in English and Arabic. Try them inside Instagram's and TikTok's in-app browsers, where the camera, storage and "Open in my browser" all behave differently. Try them on Dawn with its sticky Add to cart bar on, and on one other popular theme, including one with an Arabic storefront. Use a 390 pixel phone width as the main case, and check 320. Check the theme editor: the GRINDCTRL Store Chat embed turns chat on, the Try-On on product cards embed turns the pills on, the GrindCTRL Try-On block can be placed and moved, and in the editor both widgets show for placement whatever the launch state. Check the preview token: the owner sees both widgets, and a second browser without the token sees neither. Check the dashboard on a phone and at 1024, 1440 and 1920 pixels, in light and dark. Check the Shopify admin in English and Arabic admin, on desktop and in Shopify's mobile app. Do a keyboard-only pass of the dashboard and the admin pages. Read every new screen in Arabic against its twin, on a phone and on a desktop, and have the owner approve the drafts a surface ships before that surface goes live. Do a screen reader pass with VoiceOver on iOS through the try-on sheet and the chat panel, and with VoiceOver or NVDA on desktop through Today, Inbox and one studio. The services with test modes need their own passes: WhatsApp Cloud API in test mode with a test number (item 14), Shopify billing with test charges on a development store (item 21), and the web pixel in Shopify's pixel sandbox (item 22).

What can only be checked in production. There is no staging environment, and the demo store at `https://grindctrl.myshopify.com` (password 1) talks only to production. Theme extension changes reach stores only when the owner deploys the app version with Shopify's CLI, and database migrations in `supabase/` are applied by hand, as `AGENTS.md` describes. So every pull request that touches the extension, a migration, a scope or an environment variable must list exactly what the owner has to do after merging, in order. That includes the app version to deploy, the SQL files to apply, the scopes to approve (`read_themes`, `read_inventory` and protected customer data among them, from phase zero), and the variables to set. It must also list the checks the owner should then run on the demo store.

Every pull request carries before and after screenshots at 390 and 1440 in English and Arabic for the screens it changes. It lists the Arabic strings it ships that are still marked draft in `copy`, and any it wrote that no board shows, so the owner can review them in one place. It lists the owner decisions it depends on and which default it built until they are made. It says plainly what was verified in a real browser, what only against mocks, and what not at all. And it updates `PROGRESS.md` in this folder, so the next session knows where the work stands.
