This note lists the correctness, safety and backend work that has to land before or alongside the v16 redesign. Without it, the new screens would show numbers the back end cannot produce, or make promises the code does not keep. Every item was checked again against `main` at commit b92e71b, which includes PRs #33 to #36. Paths are relative to the repository root. Line numbers are from b92e71b. Each item says what is wrong or missing today and the evidence, what to change and where, how to test it, and which boards depend on it. Board names are the board file names in `design/prototype/boards`, without the extension, and every board's copy is in the `copy` folder.

The items fall into three bands. Band one comes first. It covers things a shopper or merchant would read on a v16 screen that are untrue today, plus two bugs that would quietly break the first busy store. Nothing shopper-facing from v16 should ship before band one is done. Band two is the new back end that individual boards need, such as shifts, WhatsApp, attribution and the 50/50 test. Each board in band two should ship together with its item, or ship without the part that depends on it. Band three is hardening that should ride along with the redesign because the new screens make the old gaps more visible. Several items need a decision from the owner before anyone can build them. Those decisions are named plainly in the item and gathered again at the end. Each board list names English boards, and each board's Arabic twin depends on the same items. `09-backend-contracts.md` gives the exact contract and flag for every feature the boards outline as new.

Band one, item 1. The Try it on button must hide itself when looks run out, and it does not. The App Proxy config route already computes availability: `apps/web-next/app/api/shopify/proxy/config/route.ts:75-80` asks `getShopEntitlement`, and lines 102-103 return `available` and `messageKey`. Neither storefront script reads them. `apps/grindctrl-tryon/extensions/tryon-block/assets/tryon.js:80-113` applies label, colours and radius, then always reveals the button. `apps/grindctrl-tryon/extensions/tryon-block/assets/tryon-catalog.js:57-64` and `:337-364` inject the card pill whatever the config says. The session and attempt routes do not check entitlement either. So the shopper uploads a photo, waits, and only then gets `TRYON_UNAVAILABLE`, which `apps/web-next/app/api/try-on/generate/route.ts:351-355` returns as HTTP 200 with the English sentence from `apps/web-next/lib/try-on/entitlement.ts:157`. The embed prints that raw text at `apps/web-next/components/try-on/try-on-demo.tsx:282`, `:300` and `:612`, even in Arabic. The fix has four parts. Return one launch field from the config route, for example `tryOn: 'live' | 'hidden'` with a reason code, computed from installed, plan status, looks left, the new launch state (item 9) and the new per-product pause (item 18). In `tryon.js`, keep the block `display: none` until config arrives and remove it when the answer is hidden. Today it uses `visibility: hidden` (`tryon.css:26-28`), which leaves an empty gap above Add to cart. In `tryon-catalog.js`, inject no pills when hidden. Also refuse early in `apps/web-next/app/api/shopify/proxy/try-on-context/route.ts` with a coded 409, so a page that was cached before the looks ran out cannot start a look. The config route caches answers in memory for 60 seconds (`config/route.ts:21-45`). Clear the cache entry for the shop when the last look is used and when looks are added, so the button really "comes back the moment you add looks". Store Chat must keep working at zero looks. That is already true: nothing under `apps/web-next/lib/messenger` reads plans or credits. To test, add a route test for the config route with an exhausted entitlement, and an extension test that runs `tryon.js` and `tryon-catalog.js` against a stubbed fetch returning hidden and asserts that no button or pill exists. Then check on a dev store whose looks are set to zero. Boards: TryOn-PDP, TryOn-States, Plan, Shopify-Plans, Shopify-Home, Today, TryOnStudio, Shopify-TryOn and Command.

Band one, item 2. The photo promise must become true. The approved promise is that the photo goes to our try-on service, makes one look, and is then deleted; that the photo and looks stay on the shopper's phone for 24 hours; and that the store only sees a look the shopper sends. Today, part of this holds and part does not. Our server does not store the source photo, as stated in `apps/web-next/lib/try-on/persistence.ts:1-4`. But the finished look is kept twice. For paid storefront looks it is stored in the private bucket `tryon-results` for 30 minutes (`persistence.ts:26-27`). Every look is also held in process memory for up to 30 minutes (`apps/web-next/lib/try-on/service.ts:35-37`), and `getJob` at `service.ts:306-308` ignores that TTL. The photo is sent to OpenRouter's Images API (`apps/web-next/lib/try-on/image-runner.ts:18` and `:128-143`) with no data-collection or zero-retention preference in the request. Store Chat already sends `provider: { data_collection: 'deny' }` at `apps/web-next/lib/messenger/chat-client.ts:45`, so the pattern exists. Nothing is kept on the shopper's phone: the embed holds the photo and the result only in React state (`try-on-demo.tsx:109-118`). The consent step is shown before every look (`try-on-demo.tsx:401-465`) and nothing records consent. The shopper copy today is a different promise: "It is not stored permanently or shared publicly" (`apps/web-next/lib/try-on/i18n.ts:183-184`, Arabic at `:324-325`). What to change: add the provider preference to the image request, and get written confirmation from OpenRouter that the Images API honours it for the model in use. If it cannot be confirmed, the owner must either soften the sentence or change the provider. On our side, delete the stored look as soon as the shopper's browser has received it, or cut retention to the poll window, and make `getJob` respect the TTL. Then decide whether the sentence should also mention that a look waits on our server for a few minutes so a reload can recover it. On the phone, keep the photo and the looks in IndexedDB in the embed's origin, each with an expiry 24 hours from when it was saved, and only while the shopper leaves "Keep my photo on this phone" on. Keep the consent flag apart, with its own longer expiry (about a year, signed off with item 34), so "We only ask this once" stays true after the photo is gone. Purge expired entries on every load, and add Delete all. The embed is a third-party iframe on the merchant's store. Chrome, Firefox and Safari partition its storage by the store's site, which matches "My looks, across the whole store". But a private window or Safari's storage clearing can lose it early, so the UI must handle "nothing saved". The third promise, that the store only sees a look the shopper sends, holds today. No dashboard or admin code reads result images: a search for `resultImageUrl` and `result_storage_path` finds only the try-on routes, the embed and the studio. Keep it that way with a test. v16 adds one new way to break it. Several boards draw the shopper's look on the merchant's own page, for example the "Your look" card on TryOn-Browse and the thumbnail in the floating chip. Session-replay and analytics scripts on a store record the page, so a look drawn there is a look the store can see. Render looks only inside our iframes (see `07-board-map.md`). Replace the copy in `lib/try-on/i18n.ts` with the approved sentences, and register them in `apps/web-next/lib/product-truth/public-register.ts`. The existing entry there, `privacy.tryon-short-private-flow` at `:152-169`, still notes at `:168` that provider retention, training, backups and deletion behaviour need policy evidence. Update `docs/legal/privacy-policy-draft.md` to match. To test: a unit test that the provider request body carries the preference; a persistence test that the stored look is gone after delivery; an embed test with a mocked clock that saves a look, moves time forward 24 hours and expects an empty store; and a manual pass in iOS Safari and in the Instagram in-app browser. Boards: TryOn-PDP, TryOn-Photo, TryOn-Check, TryOn-States, TryOn-More, TryOn-Desktop, Chat-Desktop, Studio-Phone, TryOnStudio and Shopify-TryOn.

Boards: every shopper try-on board, and the health strip on Today and Shopify-Home, which would otherwise go red for no real reason.

Band one, item 4. Looks left is computed from an unbounded ledger read, and the v16 plan sizes make that read too big. `getShopEntitlement` reads every ledger row of the subscription with no limit and no order (`apps/web-next/lib/try-on/entitlement.ts:385-388`), then sums them in JavaScript (`:403-421`). Each look writes a debit row, and each failed look writes a debit and a refund. The boards now show the catalogue's plan sizes, 350 looks a month on Growth and 650 on Pro, plus 80 for each Boost pack. Rows pile up across cycles, because the read is by subscription. If the Supabase project keeps the default PostgREST cap of 1,000 rows, the sample store, which used 300, 430 and 200 looks in its last three cycles, passes it during its third cycle, and a busy Pro store during its second. Then "150 left of 350", the alerts at 20 and 5 percent left and the `available` flag that hides the button all become wrong. The same function also runs a write-locking reconcile on every read (`:337`), including every uncached config call and every generation (`service.ts:123-125`). Move the sum into one SQL function that returns plan and top-up balances, call that from `entitlement.ts`, and stop calling the full entitlement on the generation path just to read a tier label. The same unbounded pattern sits under the numbers in item 22: `apps/web-next/lib/dashboard/overview-data.ts:230-236` pulls 14 days of `tryon_jobs` with no limit and swallows every error at `:245`, and `getOverviewStats` in `apps/web-next/lib/messenger/conversations.ts:794-831` caps reads at 500 conversations and 5,000 messages. Every number on Today, TryOnInsights and Plan should come from SQL aggregates, never from summing a page of rows in JavaScript. To test, add an SQL test against a throwaway database with 2,500 ledger rows that checks the balance, and read the "Max rows" value in the Supabase project's API settings to confirm the live cap. Boards: Plan, Shopify-Plans, Today, Owner-Phone, TryOnInsights, Shopify-Home and the sidebar meter on every dashboard board.
