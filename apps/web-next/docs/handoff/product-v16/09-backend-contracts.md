Backend contracts for v16

This note is for the engineers who connect the v16 screens to the back end that exists. For every screen it says which routes, server actions, tables, columns, enums and settings fields it uses at commit b92e71b, with path:line evidence, and for every element the boards mark as new it gives an exact contract. Paths are relative to the repository root. Board names are the board file names without the extension. Read `06-phase-zero.md` first, because many contracts below finish or extend one of its 34 items, and keep `07-board-map.md` open for where each board lives in the code.

Every board except Main has a Review switch called markNew in its props, under Review. Turn it on and every element that needs new back end work gets an orange dashed outline, and a note in the corner explains the outline. In the board markup those elements carry `data-be="new"`, so a search of one board file for that attribute gives the exact list of new work on that board. The English board files carry 261 of these attributes on 36 boards. Onboarding carries none. Main is the journey index, so it has no switch and no contract. Each Arabic twin, named like `Today-AR`, carries the same outlines as its English board and shares its contract, so this note only names English boards. The retired TryOn-Arabic, Today-Arabic and Shopify-Arabic boards are replaced by twins and have no contract of their own.

New back end work means anything that needs a new endpoint, table, column, background job, analytics event, integration or server rule. Integrations include a new Shopify scope, webhook or extension, Shopify billing, WhatsApp, and reading or changing the shopper's cart. Layout, client state, copy and storage on the shopper's own device are front end work, so they carry no outline even when they are new. Everything without an outline already has a source in the code, and the board paragraphs below name it. Plan numbers on the boards match the fallback catalogue in `apps/web-next/lib/try-on/public-catalog.ts:55-153`: Free with 15 looks, Launch at $15 for 150, Growth at $29 for 350, Pro at $49 for 650, and the Boost 80 pack, `pack-lite-v1`, at $5 for 80 looks valid 365 days (`:137-146`). The code must still render the live catalogue from `listPublicPlanCatalog` (`:194`) and the live entitlement, never numbers copied from a board. The repository SQL seeds a free plan `free-v1` with 20 looks (`supabase-migration-plans.sql:245`), while the fallback names `free-v2` with 15 (`public-catalog.ts:59-64`), so the live rows decide what prints.

The build rule is the same for every screen. Render live data from the sources named here, and leave a marked element out entirely until its contract ships. No sample numbers, no disabled teasers and no "coming soon". Each feature below has its own per-store flag, and a marked element appears only when its flag is on for that store and its contract answers. The flag store does not exist and is not in phase zero, so build it first. Put a table `store_flags` in `supabase/store_flags.sql` with `id uuid`, `shop_domain text` for a Shopify store, `widget_site_id uuid` for a Store Chat site on another website, `flag text`, `enabled boolean not null default false`, `updated_by text` and `updated_at timestamptz`, a check that exactly one of the two keys is set, and a unique index on each key with the flag. Read it through one helper, `isStoreFlagOn(store, flag)`, in a new `apps/web-next/lib/flags/store-flags.ts`, cached for 60 seconds like the App Proxy config cache (`apps/web-next/app/api/shopify/proxy/config/route.ts:21-45`). Only the platform operator flips a flag, through a server action `setStoreFlag` guarded by `requireTryOnPlatformOperator` (`apps/web-next/lib/shopify/platform-operator.ts:28`). The storefront scripts learn the store's flags from a `features` array added to `/apps/grindctrl/config` and `/api/messenger/config`. A route whose flag is off answers 404 with `{ ok: false, error: 'not_enabled' }`. Flag names are the feature code and a short name, for example `n1_shopify_billing`.

Shared conventions keep each contract short. A contract names one of six ways the caller proves who it is. A Clerk owner check is a Clerk session from `auth()` followed by `requireManagedTryOnShop` (`apps/web-next/lib/shopify/shops.ts:118`) for a try-on shop, or `requireOwnedSite` (`apps/web-next/app/dashboard/messenger/actions.ts:50`) for a Store Chat site, which also spends the merchant read or write budget. A Shopify session token is `authenticateShopifyRequest` (`apps/web-next/lib/shopify/session-token.ts:85`), which yields the shop and nothing about the staff member (`:15`), followed by `merchantRateLimitResponse` keyed `shop:<domain>` (`apps/web-next/lib/request-rate-limit.ts:75`). An App Proxy signature is `verifyShopifyProxySignature` (`apps/web-next/lib/messenger/identity.ts:41`) with the stale request check, as `apps/web-next/app/api/shopify/proxy/try-on-context/route.ts:58-67` does. The config route skips it today (`config/route.ts:13-14`), so anything sensitive added there must add the check. The widget origin proof is `resolveShopperSession` (`apps/web-next/lib/messenger/public-session.ts:32`): a valid embed key, a live site, an origin admitted through the signed origin token (`identity.ts:197` and `:222`), a visitor under that site, and a conversation under that visitor. A try-on capability is the signed context, session and attempt tokens from `apps/web-next/lib/try-on/storefront-context.ts:242`, `:370` and `:503`. An internal secret is a Bearer secret compared in constant time, as the cleanup job does in `apps/web-next/app/api/internal/try-on/cleanup/route.ts:12-24`. New Shopify webhook topics reuse the HMAC check in `apps/web-next/app/api/shopify/webhooks/route.ts:8-30`.

Routes answer `{ ok: true, ... }` or `{ ok: false, error: '<code>' }` with the status the contract names, and 429 or 503 always come from `rateLimitErrorResponse` (`lib/request-rate-limit.ts:57`). Server actions return the existing `ActionResult` (`apps/web-next/lib/messenger/actions-core.ts:28`) or `MerchantActionFailure` (`lib/request-rate-limit.ts:8-13`). Every limit goes through `requireRateLimit` (`:37`), which refuses with 503 when Redis is missing. New limiters sit beside the four in `apps/web-next/lib/ratelimit.ts:87-90`, and storefront limits on App Proxy routes must not key on `clientIp` alone (phase zero item 3). Dashboard pages are server components, so a dashboard read below is a function in `lib` that the page calls after the owner check, and the Shopify admin gets the same JSON from a route under `app/api/shopify/admin/` or `app/api/shopify/store-chat/` on the session token. SQL goes in the root `supabase` folder as idempotent files: `begin` and `commit`, `create table if not exists` and `add column if not exists`, row level security on, everything revoked from `anon` and `authenticated`, grants to `service_role` only, and a commented rollback, like `supabase/20260910_tryon_shop_links.sql:18-36`. File names below leave out the date prefix that the newest files carry. They are applied by hand in the Supabase SQL editor (`supabase-migration-shops.sql:2`). Tests are Vitest beside the code (`apps/web-next/package.json:11`), with route tests next to the route as in `apps/web-next/app/api/shopify/proxy/try-on-context/route.test.ts`, and Playwright for end to end (`package.json:13`). Every flagged contract gets one extra test: with the flag off, the route says `not_enabled` and the public payload leaves the feature out. Every new table that holds shopper or staff data needs a rule in the export and in both erasure handlers of `apps/web-next/lib/shopify/privacy.ts` (phase zero item 34).
