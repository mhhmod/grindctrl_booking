## Implementation decisions and fixed defects

1. Keep the existing SaaS/merchant identity, dashboard, AI engines, settings, subscriptions and ledger. No neutral-store rewrite or new platform adapter belongs to this milestone.
2. Add `shopify_installations`, keyed by shop plus registration with an internal UUID, rather than modifying ambiguous legacy token ownership. New encrypted access/refresh material, lifetime metadata and lifecycle status belong to the installation.
3. Serialize acquisition and refresh using a distributed PostgreSQL lease, not an in-process mutex. Fence writes against lease ownership; acquisition and refresh cannot intentionally retire each other's results. Unknown outcomes are not automatically retried.
4. Record lifecycle events and installation-local mutations transactionally. App A cannot delete B's credentials; late pre-authorization events are ignored, uncertain ordering is recorded for manual handling, and scopes notifications never globally reactivate stores. Credentials rejected with 401 are retired by matching version.
5. Validate ID token algorithm/signature/audience/expiry/not-before/issuer/destination/subject; retain the verified registration. Embedded privileged routes also verify that installation is active. Reject shared app secrets and conflicting registration configuration.
6. Resolve App Bridge from a configured per-app entry or a verified ID token. A single configured app keeps the original development entry; ambiguous multi-app entries are refused. Theme/admin links no longer use a fixed global client ID and have ownership/rate-limit regression tests.
7. Pass the verified app into product resolution and cache keys. Store-level consumers without app context use only a sole active installation; ambiguity fails closed. Verified shopper identity retains application provenance and active-installation checks before order use. Anonymous order proof remains order number plus matching email; no new order-write capability is introduced.
8. Introduce independent core capability signing for public demo, preview, claim and iframe origin proof. Platform signatures are still used for Shopify-specific capabilities; a Shopify app secret cannot mint a public-demo authorization.
9. Replace the unsafe shared-data privacy deletion path with durable app-scoped receipts and manual escalation. A recorded/alerted request is NOT fulfilled. Privacy fulfillment remains a documented release blocker requiring approved scope/retention/execution evidence.
10. Patch the runtime dependency audit findings in nodemailer (10.0.12 to 10.2.1) and fast-uri (3.1.8 to 3.1.9), within existing compatible ranges. Preserve unrelated lockfile platform metadata. Production dependency audit subsequently reports zero vulnerabilities.
11. Follow-up audit found a remaining first-app signer in the optional unsigned/nonbillable legacy storefront bridge. It now requires a sole configured registration before fetching a product, passes that exact app to product resolution and preserves the single-app fallback. Registry documentation no longer describes a distribution bypass or core capabilities as Shopify-signed.
12. Follow-up lifecycle audit found that a still-valid storefront capability could authorize new Try-On work after A's uninstall while B kept the merchant active. Session/attempt/generation now check the signing installation; proxy availability checks occur before the shared merchant cache. Existing reserved jobs retain their merchant/request/credit identity and can settle without another Shopify credential. Three paused-provider transition tests cover completion, failure and finalization-pending replay without another provider call. This is orchestration evidence with mocked persistence, not proof of deployed ledger reconciliation.

## Compatibility and remaining gates

- **P0 / launch blocker:** Shared customer/site/job ownership and retention rules have not been approved. No automatic privacy redaction is allowed on this branch. All pending new and legacy requests require accountable, compliant handling; approval of architecture does not close this gate.
- **P1 / external verification:** Target Supabase project/data/schema/RLS/backup status and real Shopify distribution/permissions/extension releases remain unavailable, not presumed empty or correctly configured.
- **P1 / compatibility:** Legacy tokens require reauthorization; fresh expiring credentials may retire earlier tokens. No guessed backfill or promise that an old image can reuse them.
- **P1 / overlap:** A store with two active installations and no verified app context is deliberately unavailable for that credential-dependent operation. A prolonged coexistence preference UI is not implemented. Use the correct embedded entry and audit the cutover procedure before a pilot.
- **P1 / lifecycle evidence:** Triggered-At ordering is a hint carried in headers, not signed installation-generation proof. Captured-message/header replay and real delayed Shopify deliveries require independent threat review and Development Store evidence before merchant rollout.
- **P1 / real product evidence:** No authenticated real Development Store installation/refresh/browser/cart/order/AI generation was executed. Local mocks and SQL tests cannot establish platform approvals, protected fields, model quality or actual merchant readiness.
- **P1 / pending jobs:** Actual job/ledger snapshots, reconciliation function definitions/schedules and private result cleanup remain unverified. Keep the former app's verification configuration through the bounded capability drain window unless revoked for security; otherwise old polling capabilities stop verifying. The checked-in entitlement reconciliation schedule is daily, not proof of the ten-minute sweep mentioned in historical comments.
- **P1 / commercial dependency:** Billing integration is deferred. No new paid pricing, checkout or unrestricted manual grant is added. Public submission still needs an applicable, approved Shopify billing/free-pilot decision.
- **P1 / development toolchain review:** Full dependency audit reports 13 findings (5 moderate, 6 high, 2 critical); the production-only audit reports zero. Critical chains involve Vitest/Tinypool, and the suggested Vitest fix is a major-version upgrade. These findings are not remediated by this Shopify patch. Review exploitability and toolchain remediation separately before approving merge or exposing development/test servers. Do not interpret the production-only audit as a clean full dependency graph.
- **P2:** Existing Sentry import deprecation warning is unrelated to this change; it remains a future maintenance item.
- **P2 / local test timing:** Concurrent local build/full-suite execution exposed one-second FileReader/UI wait sensitivity in the unchanged Try-On demo test. An under-load isolated rerun also failed; the same unmodified file passed 6/6 without competing work, and the complete CI unit gate passed. No production assertion or test timeout was loosened. Local interrupted/failed attempts are not reported as a passing complete suite.

## Migration and rollback

One reviewed manual additive delta is required: `supabase/20261024_shopify_installation_isolation.sql`. It was tested only in isolated local PostgreSQL (PGlite); it was NOT applied to Supabase. Existing merchant/credit/subscription/legacy-token tables are not purged or backfilled. `shopify_credential_audit` links to the installation UUID. Browser roles have no credential/event access.

The existing merchant table remains authoritative; no new merchant, subscription, credit account or registration table is introduced. Credentials live on the installation row. Primary keys and unique `(shop_domain, app_client_id)` / `(app_client_id, webhook_id)` constraints create the identity/dedupe indexes. Encryption-envelope and lease-pair checks reject incomplete field groups. Credential audit has an installation FK without a cascading delete. Event receipts intentionally need no installation FK because mandatory/privacy events can arrive for unknown or historical installations and must still be durably recorded. Registrations remain server configuration validated before authentication. RLS plus explicit browser-role revocations and service-role-only mutation RPC grants are part of the delta; actual hosted grant/RLS drift remains unverified.

See [the runbook](2026-10-24-shopify-m1-runbook.md) for read-only preflight, approved migration order, secret/configuration dependencies, legacy reauthorization, privacy monitoring and rollback limitations. Schema rollback cannot restore retired Shopify credentials or undo deletion; no deletion was performed by this work.
