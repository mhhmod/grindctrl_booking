## End-to-end flow

1. WordPress's update check reads our Update URI and invokes `update_plugins_grindctrl.cloud`. We return nothing for another basename. For our plugin we read cached metadata or GET `/api/woo/plugin/update` over HTTPS, without cookies or connection credentials.
2. The server enforces the shared fail-closed public limiter and serves the generated release metadata. WordPress receives the slug, latest version, compatibility, homepage and versioned package URL. It compares versions and shows its standard update notice when a later release is available. SHA-256 travels with that advertised core update record.
3. Opening View details invokes `plugins_api`. Our handler returns plugin information and sanitized description/changelog sections from the same metadata cache.
4. When WordPress runs an opted-in background update, or the merchant chooses Update now, `upgrader_pre_download` matches the exact advertised URL. It rejects missing/invalid SHA-256, downloads the file, computes SHA-256, compares with `hash_equals`, deletes a mismatch and returns an error. Only verified bytes are returned to WordPress for unpacking. Other package URLs are untouched.
5. Keeping the checksum in core's retained update metadata avoids coupling an already scheduled update to a newly published release or an expired custom cache. An old URL whose bytes have changed fails safely rather than installing unexpected bytes.
6. On the next load of the new plugin, the version-change routine preserves settings and connection, restores missing heartbeat scheduling, and records the new version. It never re-enables auto-updates after the defaulted flag has been written.

This uses the documented WordPress [Update URI hostname filter](https://developer.wordpress.org/reference/hooks/update_plugins_hostname/) and [upgrader pre-download filter](https://developer.wordpress.org/reference/hooks/upgrader_pre_download/). Integrity here is SHA-256 metadata delivered over HTTPS, as requested; it is not a separate public-key signature scheme.

## Getting 0.3.7 merchants onto 0.4.0

0.3.7 contains no private updater. It needs one last manual update: download the current ZIP from the GRINDCTRL dashboard, then use WordPress Plugins > Add New Plugin > Upload Plugin and replace the installed version with the uploaded ZIP. Use replacement rather than deleting the existing plugin, since uninstall removes connection settings.

The existing notice in `plugin/grindctrl-store-chat.php:585` says exactly:

> A newer GRINDCTRL Store Chat plugin is required. Download the current version from the dashboard.

That notice appears only when the heartbeat/pair response's minimum version exceeds the installed version. Since the minimum remains 0.2.0, this change does not cause that notice to appear on 0.3.7. After the manual replacement, 0.4.0 opts into native auto-updates once. The merchant can disable them from the normal Plugins screen. A 0.4.0 install already matches this release; observing an actual later-version update needs a subsequent test release.
